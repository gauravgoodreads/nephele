# 0006. Defence in depth: restricted Pod Security, NetworkPolicies, non-root images

## Context

The upstream images ran as root, the vote and result services listened on
port 80, and any pod in the cluster could connect to the database.

## Decision

Several independent layers, so one mistake does not expose everything:

1. **Images:** every application image runs as a non-root user on an
   unprivileged port (vote uid 10001 on 8080, result uid 1000 on 8080,
   worker uid 1654); CI fails a build whose image runs as root.
2. **Pod Security Admission:** the `nephele` namespace enforces the
   `restricted` profile: non-root, no privilege escalation, all Linux
   capabilities dropped, seccomp on. Every container also has a read-only
   root file system, with `/tmp` as an in-memory volume where needed.
3. **NetworkPolicies:** only pods labelled `db-client` reach PostgreSQL and
   only pods labelled `redis-client` (plus KEDA) reach Redis.
4. **Governance:** a LimitRange and ResourceQuota stop one workload from
   consuming the whole cluster.
5. **Secrets** in Kubernetes Secrets (on AWS, generated by Terraform and
   injected by the pipeline), never in images or Git.
6. **Supply chain:** Trivy scans every image in CI; ECR scans on push.

## Consequences

- Postgres and Redis needed explicit user IDs, writable volumes for their
  sockets and data, and `fsGroup` so they can own their disks.
- Debugging inside containers is harder (no shell tools as root).

## Evidence

Chaos test 7 (an unlabelled pod is blocked from the database) and test 9
(a root pod is refused by the API server).
